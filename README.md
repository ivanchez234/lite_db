# lite_db

[![CI](https://github.com/ivanchez234/lite_db/actions/workflows/ci.yml/badge.svg)](https://github.com/ivanchez234/lite_db/actions/workflows/ci.yml)
![C++17](https://img.shields.io/badge/C%2B%2B-17-blue)
![Linux | Windows](https://img.shields.io/badge/platform-Linux%20%7C%20Windows-lightgrey)
[![License: MIT](https://img.shields.io/badge/license-MIT-green)](LICENSE)

**lite_db** — клиент-серверная СУБД на C++17, написанная с нуля, чтобы разобраться, как база данных устроена изнутри. Сервер хранит таблицы в собственном формате со сжатием, переживает аварийное завершение благодаря журналу предзаписи и обслуживает клиентов по TCP. Запросы можно отправлять текстовыми командами, на подмножестве SQL или из Python через драйвер DB-API 2.0.

> [!NOTE]
> Учебный проект: начинался как курсовая по САОД (структуры и алгоритмы обработки данных). Для хранения настоящих данных он не предназначен.

## Возможности

- **Таблицы со схемой:** типы `STRING`, `INT`, `DOUBLE`, `BOOL`, `DATE`, целочисленный ключ `id`, строгая проверка данных по схеме.
- **Запросы:** вставка, частичное обновление, удаление, чтение записи, одного поля или всей таблицы; пакетная вставка `MPUT`; подмножество SQL.
- **Хранение:** сжатые zlib блоки с колоночной раскладкой в дописываемых сегментах, индекс по `id` в памяти, кеш распакованных блоков.
- **Надёжность:** журнал предзаписи с CRC32 и групповым коммитом. Всё, на что клиент получил `OK`, восстанавливается после `kill -9`.
- **Многопоточный сервер:** клиенты работают параллельно, каждому ответы приходят в порядке его запросов, Ctrl+C корректно сохраняет данные.
- **Python:** драйвер по стандарту DB-API 2.0 и диалект SQLAlchemy.
- **Проверки:** 65 тестов, CI на Linux и Windows с AddressSanitizer, ThreadSanitizer и clang-tidy.

## Быстрый старт

### Что нужно

CMake 3.14 или новее, компилятор с C++17, zlib и git. Python 3 нужен только для драйвера, сквозного теста и скриптов замеров.

| Система | Установка зависимостей |
|---|---|
| Ubuntu / Debian | `sudo apt install build-essential cmake git zlib1g-dev python3` |
| Windows (терминал MSYS2 UCRT64) | `pacman -S git mingw-w64-ucrt-x86_64-gcc mingw-w64-ucrt-x86_64-cmake mingw-w64-ucrt-x86_64-ninja mingw-w64-ucrt-x86_64-zlib mingw-w64-ucrt-x86_64-python` |

### Сборка

```bash
git clone https://github.com/ivanchez234/lite_db.git
cd lite_db
cmake -S . -B build              # на Windows: cmake -S . -B build -G Ninja
cmake --build build -j
ctest --test-dir build           # необязательно: прогнать тесты
```

При первой сборке CMake скачивает тестовый фреймворк Catch2. Чтобы собрать только сервер и клиент, без тестов и без скачивания, добавьте `-DLITE_DB_BUILD_TESTS=OFF`.

### Запуск

В первом терминале — сервер, во втором — консольный клиент:

```bash
./build/server_app        # слушает 127.0.0.1:5555
./build/client_app        # подключается к 127.0.0.1:5555
```

Сервер читает `setup.yaml` и хранит данные (`data/`, `wal.log`) в каталоге, откуда его запустили. Другой порт и адрес: `./build/server_app 6000 0.0.0.0`.

Пример сеанса в `client_app`:

```text
> CREATE users
OK: Table 'users' created
> SCHEMA users name:STRING age:INT is_active:BOOL
OK: Schema applied
> INSERT users 1 {"name": "Ivan", "age": 21, "is_active": true}
OK
> INSERT INTO users (id, name, age, is_active) VALUES (2, 'Maria', 22, 0)
OK
> SELECT * FROM users WHERE id = 2
{"name":"Maria","age":22,"is_active":false}
> UPDATE users 2 {"age": 23}
OK
> SELECT users 2 age
23
> INSERT users 3 {"name": "Bob", "age": "old", "is_active": true}
ERR_CONSTRAINT_VIOLATION
```

Ctrl+C в окне сервера останавливает его: сервер дожидается всех потоков, сбрасывает данные на диск и очищает журнал. Таблицы сохраняются между запусками.

### Из Python

При запущенном сервере, из корня репозитория:

```python
import litedb_driver as db

with db.connect(port=5555) as conn:
    cur = conn.cursor()
    cur.execute("INSERT INTO users (id, name, age, is_active) VALUES (?, ?, ?, ?)",
                (10, "Anna", 30, True))
    cur.execute("SELECT * FROM users WHERE id = ?", (10,))
    print(cur.fetchone())   # ('Anna', 30, True)
```

## Использование

Протокол текстовый: одна команда — одна строка, один ответ — одна строка.

| Команда | Пример | Ответ |
|---|---|---|
| Создать таблицу | `CREATE users` | `OK: Table 'users' created` |
| Задать схему | `SCHEMA users name:STRING age:INT is_active:BOOL` | `OK: Schema applied` |
| Вставить | `INSERT users 1 {"name": "Ivan", "age": 21, "is_active": true}` | `OK` / `ERR_ID_EXISTS` |
| Изменить поля | `UPDATE users 1 {"age": 22}` | `OK` / `ERR_NOT_FOUND` |
| Прочитать запись | `SELECT users 1` | JSON записи / `ERR_NOT_FOUND` |
| Прочитать поле | `SELECT users 1 name` | значение поля |
| Прочитать таблицу | `SELECT users ALL` | JSON-массив `[{ "id": ..., "data": {...} }, ...]` |
| Вставить пакет | `MPUT users 1 {...} 2 {...} 3 {...}` | `OK` или ошибка, и тогда не вставлено ничего |
| Удалить | `DELETE users 1` | `OK` / `ERR_NOT_FOUND` |
| Сбросить на диск | `FLUSH` | `OK: All buffers flushed to disk` |
| Счётчики сервера | `STATS` | JSON: записи журнала, fsync, блоки, попадания в кеш |

SQL поддерживается в объёме, достаточном для SQLAlchemy: `INSERT INTO`, `SELECT * FROM ... [WHERE id = n]`, `UPDATE ... SET ... WHERE id = n`, `DELETE FROM ... WHERE id = n`. Правила SQL, коды ошибок и драйвер Python описаны в [docs/protocol.md](docs/protocol.md).

### Настройки `setup.yaml`

| Ключ | По умолчанию | Что задаёт |
|---|---|---|
| `wal_sync` | `full` | надёжность журнала: `none` — только буфер процесса, `flush` — переживает падение процесса, `full` — fsync на каждую запись, переживает и потерю питания |
| `block_cache_mb` | `32` | размер кеша распакованных блоков в МБ, 0 — выключен |
| `block_size_kb` | `4` | сколько КБ записей копить перед сжатием в блок |
| `tables` | — | таблицы и схемы, которые создаются при старте сервера |

## Как это устроено

```text
клиент ──TCP──▶ TcpServer ──▶ Database ──▶ журнал (wal.log) ──▶ Storage ──▶ data/<таблица>/seg_N.db
                 потоки         SQL → команды     fsync           буфер → блок 4 КБ → zlib
```

Запись подтверждается клиенту только после того, как попала в журнал; данные копятся в буфере таблицы и по 4 КБ сжимаются в блок. Чтение ищет запись сначала в буфере, затем по индексу в блоке на диске или в кеше.

### Технологии

| Задача | Чем реализовано |
|---|---|
| Язык и сборка | C++17, CMake; тестовый фреймворк подтягивается через `FetchContent` |
| Сеть | TCP-сокеты (POSIX и Winsock2) за RAII-обёрткой, `poll`/`select` с таймаутом, `TCP_NODELAY`, свой построчный текстовый протокол |
| Многопоточность | `std::thread`: поток приёма, поток чтения на соединение, пул из 5 рабочих потоков; очереди на `std::condition_variable`; `std::shared_mutex` (читатели параллельно, писатель эксклюзивно); `std::atomic` для счётчиков |
| Хранение | Свой бинарный формат: дописываемые сегменты, блоки 4 КБ, колоночная перепаковка, дельта-кодирование `id`, битовая упаковка `BOOL`, сжатие zlib; индекс `std::unordered_map` в памяти |
| Кеш | LRU-кеш распакованных блоков: `std::list` + `std::unordered_map`, 8 шардов со своими мьютексами, блоки через `std::shared_ptr` |
| Надёжность | Журнал предзаписи (частичная реализация транзакций) с CRC32 (zlib), `fsync` / `FlushFileBuffers`, групповой коммит, `fsync` каталогов при контрольной точке |
| Разбор запросов | Свой JSON-парсер в один проход; транслятор подмножества SQL: ручной разбор за линейное время, `std::regex` только для коротких фрагментов |
| Python | Драйвер по стандарту DB-API 2.0 (PEP 249), диалект SQLAlchemy |
| Тесты | Catch2 v3, CTest, сквозной тест на Python с настоящим сервером (`kill`, Ctrl+C) |
| Качество | GitHub Actions: Linux (GCC, Clang) и Windows (MSYS2 UCRT64), AddressSanitizer + UBSan, ThreadSanitizer, clang-tidy с ошибкой на любое предупреждение |
| Замеры | Свой нагрузочный клиент на C++ (пропускная способность и перцентили задержек), скрипты на Python, сравнение размера с SQLite |

Подробно — компоненты, формат файлов байт за байтом, журнал и замки: [docs/architecture.md](docs/architecture.md).

## Производительность

Замеры сняты на двух стендах. Абсолютные числа на другом железе будут другими, особенно всё, что ждёт fsync.

| | Стенд A | Стенд B |
|---|---|---|
| Машина | облачная ВМ: Intel Xeon 2,8 ГГц, 2 vCPU, 7 ГБ | ноутбук Honor MagicBook: AMD Ryzen 7 8845HS, 8 ядер / 16 потоков, 16 ГБ |
| ОС, диск | Ubuntu 24.04 (Linux 6.18), ext4, fsync ≈ 0,3 мс | Windows 11, NVMe SSD KIOXIA BG5 1 ТБ, NTFS, `FlushFileBuffers` ≈ 0,75 мс |
| Сборка | GCC 13.3, Release | MSYS2 UCRT64 GCC 16.1, Release |

Клиент и сервер на одной машине (loopback), медиана из 3 повторов, режим журнала `full`, если не указано иное.

| Сценарий | Стенд A | Стенд B |
|---|---:|---:|
| вставка по одной строке, 1 клиент | 2 447 строк/с | 1 144 строк/с |
| вставка пакетами `MPUT` по 100 строк | 59 546 строк/с | 40 550 строк/с |
| вставка, 4 клиента в 4 таблицы (групповой коммит) | 4 037 строк/с | 2 066 строк/с |
| чтение с диска, 4 клиента, кеш блоков 64 МБ | 24 810 строк/с | 45 921 строк/с |
| чтение, 1 клиент, конвейер по 16 команд | 37 037 строк/с | 35 216 строк/с |

На четырёх тестовых наборах данных lite_db занимает на диске в 1,7–6,3 раза меньше места, чем SQLite: SQLite данные не сжимает. Методика, полные таблицы, эффект каждой оптимизации и выбор размера блока: [docs/benchmarks.md](docs/benchmarks.md). Повторить замеры: `python benchmarks/run.py --build build`. Скрипт печатает процессор, ОС и тип сборки — приводите их вместе со своими числами.

## Тесты и CI

```bash
ctest --test-dir build --output-on-failure
```

65 тестов на Catch2 (формат файлов, журнал, восстановление после сбоя, многопоточность, сервер) и сквозной тест на Python с настоящим сервером: остановка по Ctrl+C и восстановление после `kill`. CI на каждый push собирает проект на Linux (Release, ASan+UBSan, TSan) и Windows (MSYS2 UCRT64) и прогоняет clang-tidy, где любое предупреждение — ошибка. Что проверяет каждый файл: [docs/testing.md](docs/testing.md).

## Что я узнал

Проект начинался как курсовая, а потом стало интересно разобраться, как база данных устроена изнутри. Почти всё здесь было для меня новым: многопоточность, колоночное хранение, сжатие, сокеты. Самыми сложными оказались надёжность записи (частичная реализация транзакций) и многопоточность.

Что я сделал бы иначе, если бы начинал заново:

- **Модель многопоточности до кода, а не по ходу.** Кто чем владеет, какие замки, в каком порядке их брать. Замки, добавленные по мере надобности, сначала просто сериализовали всю базу: пять рабочих потоков работали как один.
- **Формат файлов с версией и проверками с самого начала.** Метка формата в записи пишется, но не проверяется, у блоков нет версии, а поля опознаются только по хешу имени. Коллизию хешей я нашёл, только когда заново разбирал код, и исправил её с тестом, который без исправления падает.

## Планы

- **Транзакции.** `BEGIN` / `COMMIT` / `ROLLBACK` поверх журнала: команды копятся в наборе изменений соединения, `COMMIT` пишет их одной записью журнала под замками таблиц, `ROLLBACK` просто выбрасывает набор. Затем изоляция через оптимистичную проверку версий.
- **Разрешение коллизий хешей.** Хранить имя поля рядом с хешем и искать поле как в хеш-таблице с цепочками: хеш выбирает цепочку, имя сравнивается целиком. Тогда коллизию можно разрешить, а не отвергать.
- **ORM для C++.** Структура C++ описывает таблицу, объекты сохраняются и читаются без ручной сборки JSON.
